# 完整源码获取与证据审读协议

版本：2026-11-18。本文根据本会话可见讨论重建，不是原 ZIP 的逐字恢复。目标是让研究路线建立在可核查的已有实现上；本交接本身不代表任何第三方源码已完成获取或审读。

## 1. “参考全部源码”的可检查含义

对会影响研究定位、算法选择、强基线或工程复用的相关工作，取得选定版本的**完整可获取源码树**，建立全树索引与覆盖台账，再追踪关键行为。不以 README、论文摘要、接口名称或自动检索命中替代实现证据。

完整范围至少包括：

- 库与应用源码、命令入口、编译和运行配置。
- 测试、测试输入、示例、基准、代码生成器及生成规则。
- 所需子模块、实际使用的绑定／后端、LFS 对象和公开补充源码。
- 许可证、论文对应版本、当前版本及可访问的归档来源。

按第三方许可证使用源码；完整取得不意味着把所有第三方内容复制进本仓库。通常保留外部 checkout、锁定清单、获取方法和审计证据即可。若源码无法访问，记录尝试与结论边界；不把“未找到”写成“前人未实现”。

“全部”必须有明确的仓库／提交／路径集合。若声称“通读全部源码”，该集合内每个文件都必须有阅读记录；目录索引或搜索命中不支持这个说法。与当前任务无关的文件可以记录排除理由，但不能同时计入“已通读”的分母。

## 2. 五种状态分别记录

| 状态 | 必须具备的证据 | 不能推出什么 |
|---|---|---|
| `acquired` 已获取 | 固定完整 commit、全树文件可用、必要子模块／LFS／附件状态清楚 | 已理解实现、可运行或符合目标语义 |
| `indexed` 已索引 | 全路径清单、模块职责、版本和内容校验信息 | 已读完源码 |
| `read` 已阅读 | 逐文件阅读者／时间／职责摘要／问题记录 | 关键行为已追踪或运行过 |
| `behavior_traced` 已追踪 | 入口→核心算法→状态变化→输出／失败→测试的证据链 | 实际环境可运行或能达到论文性能 |
| `executed` 已执行 | 命令、依赖、输入、日志和结果；包括失败结果 | 科学正确性、普遍性或速度收益已证明 |

这些状态不是只能单调排列的标签：一个模块的测试可先运行，再深入读实现；必须分别记录证据。`executed` 要同时记录成功／失败及其原因。缺失输入或依赖不能算执行通过。

`sources.lock.json`、自动清点报告、`source_coverage.csv` 和 `claim_evidence.csv` 分工不同。自动工具只能提供索引与完整性线索，不代替人工判定 `acquired`，更不能自动填 `read=true`。

## 3. 首轮获取与固定版本

1. 从 [起始目录](../sources/CATALOG.md) 建立来源队列，并沿论文、作者主页、官方组织与真实依赖补充直接相关工作。
2. 为每个对象确定身份：作者原始实现、官方后续版本、第三方适配、fork 或仅方法背景。不要把不同对象合并成一个“已审计项目”。
3. 优先获得非稀疏的完整 checkout；固定完整 commit SHA 与 tree SHA，记录 URL、获取时间、许可证、tag 与论文关系。
4. 分别检查子模块、LFS 指针、生成代码、未提交构建产物、补充材料和依赖的数据。标明哪些内容属于源码、验证数据或可选资源。
5. 运行清点工具，人工审查缺失文件、脏状态、对象缺口和校验结果；把尚未取得的内容登记到缺口表。
6. 完整工作树不等于完整 Git 历史。如果仅取得单提交归档或浅克隆，照实记录；需要论文版本比较时补齐相关历史，不把浅克隆当全历史。

建议每条锁定记录至少包含：

```json
{
  "id": "<stable-id>",
  "repository_url": "<official-url>",
  "role": "paper_version | current | adaptation | fork",
  "commit": "<full-commit-sha>",
  "tree": "<full-tree-sha>",
  "retrieved_at_utc": "<ISO-8601>",
  "license": "<identifier-or-path>",
  "checkout_kind": "full-tree | source-archive | partial",
  "history_scope": "full | shallow | single-commit-archive",
  "submodules": [],
  "lfs": {"required": false, "status": "not_assessed"},
  "acquisition_status": "pending_review",
  "inventory_path": "<path>",
  "known_gaps": []
}
```

若源码仅以归档发布，保存官方 URL、归档 SHA-256、展开后的完整索引和版本出处；不要伪造 Git commit。清点脚本仅支持已有 Git checkout，归档应另建清单。

## 4. 本地清点工具

本仓库的 [inventory_sources.py](../tools/inventory_sources.py) 使用 Python 标准库与本地 Git，只清点已存在的 checkout：

```bash
cd handoff/gqcdataset_codex_goal
python tools/inventory_sources.py /path/to/external/project \
  --recurse-submodules \
  --json research/inventories/project.json \
  --csv research/inventories/project.csv
```

输出必须位于被审计 checkout 之外。工具不 clone、不获取 LFS、不初始化子模块、不安装依赖、不执行仓库代码，也不修改被审计仓库。Git 的可选索引写锁、fsmonitor、lazy fetch 和默认网络协议被关闭。

清点内容包括：HEAD／tree／分支、对象格式、脏状态、固定提交的全部文件及 blob ID、工作树字节 SHA-256／大小、缺失或替换文件、符号链接、子模块 pin 与检出状态、LFS 指针及已展开对象的内容验证。使用 NUL 分隔的 Git 输出，路径中的空格、制表符与换行不会被误拆成其他文件。JSON 使用转义编码以保留非 UTF-8 路径；CSV 对不能表示的字节作转义，JSON 是更完整的机器记录。

工具的返回码 0 表示清点完成，**不是完整获取通过**；缺失、LFS 未展开、版本不符、脏工作树等列在 `acquisition_blockers`。它只自动设置 `indexed=true`，始终保持 `read=false`、`behavior_traced=false`、`executed=false`。

限制：工作树过滤器或换行转换可导致工作树 blob 与提交 blob 不同，这需要人工解释；本工具不运行过滤器。工具识别固定提交中不超过 1 KiB 的标准 LFS 指针，更长的非典型指针或其他外部内容管理系统需要另查。清点是瞬时观察，不锁定整个工作树；不要在审计时同时修改 checkout。文件存在与校验通过，也不能证明公开源码包含论文的全部实现。

## 5. 完整索引之后如何阅读

先建立全树职责图：核心算法、科学身份／表示、求解器与导数、执行调度、持久化、接口、测试与基准、生成器和平台配置。逐文件记录到 [覆盖模板](../templates/source_coverage.csv)。

按对研究结论的影响安排阅读次序：

1. 影响“前人已有何能力”或“我们有什么可继承”的核心路径。
2. 能推翻该能力范围的边界、失败分支、未实现后端与测试缺口。
3. 验证核心行为所需的数值、格式、构建和依赖细节。
4. 与当前候选路线有关的其他模块；暂未阅读部分保持可见。

代码生成系统要同时追踪生成规则和生成结果。Python 接口调用 C／C++／Fortran／设备后端时，不能只读包装层。类型声明、注册表或文档中出现一个能力，不证明所有后端、数值阶数、模型或执行路径已支持它。

## 6. 每个重要主张必须能追踪

使用 [仓库审计模板](../templates/repository_audit.md) 和 [主张证据表](../templates/claim_evidence.csv) 记录：

**入口与输入条件 → 科学身份与状态语义 → 核心实现／调用链 → 输出与失效条件 → 失败行为 → 测试或最小验证。**

与本项目直接相关的核查例子：

- checkpoint 存了什么？恢复它是读取固定态、建立初猜，还是确实跳过目标求解？
- 密度、轨道与算符的单位、基组参数、排序、归一化、相位、自旋和原点是否匹配？
- 值已知的状态在自动微分中是否仍保留驻点方程、外场／坐标依赖和响应贡献？
- 缓存键是否包含方法、几何、表示、数值协议、状态分支以及目标约定？何时失效？
- 多目标是否真正共享求解、积分或响应，还是仅共用 Python 对象？
- 批处理是原生异构执行、填充、分桶还是循环包装？失败能否逐样本恢复？
- 质量证据是残差、经验比较、校准估计还是严格界？是否检查条件性与状态分支？

链接固定到 commit；同时写出路径与符号，便于代码移动后的追踪。测试存在、测试通过和科学结论成立是不同证据。只运行能消除具体不确定性的最小验证，保留负结果，不为增加检查数量而重复测试。

## 7. 源码审计如何进入路线判断

对每个候选创新，形成一页可审查的比较：最接近工作、具体已实现机制、可继承能力、剩余问题、竞争解释、可证伪假设、强基线和下一项验证。已有实现不必具备完全相同的项目名称才算前人；要比较机制与科学条件。

首轮获取与索引覆盖应尽可能完整，深度审读可以和验证并行推进。当影响某个假设的实现、条件、失败边界和测试已经追踪清楚，就开展能改变判断的验证，不等所有背景仓库逐行读完。尚未审读的相关源码必须作为结论限制继续挂账。

阶段完成的条件是**证据足以支持当前决策且缺口可见**，不是宣布所有仓库已读。资料获取受阻时可继续其他独立路径；不允许以访问缺口为依据证明新颖性。

## 8. 输出与完成标准

- 固定版本与许可清单：每个直接相关对象有完整 commit／归档校验和及身份说明。
- 全树索引与来源缺口表：必要子模块、LFS、补充源码和测试数据均有状态。
- 覆盖台账：逐文件区分获取、索引、阅读、追踪与执行。
- 机制证据：影响路线的主张均连到固定源码与测试／日志，未验证项明确。
- 基线清单：成熟后处理、合理热启动、缓存、批处理、组合计算和适用学习基线均被认真比较。
- 路线反馈：继承能力、创新假设、反例、适用边界和下一项验证可交给另一位执行者复核。
